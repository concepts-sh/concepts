# Best practices

What makes a base clear, correct and essential, learned from writing them. The spec says what is valid; this page says what is good.

## Write the description first

The description is the only sentence most readers will ever see, because it is the one that sits in the map on every turn. Write it before the body, and test it: can a reader use the concept correctly from this sentence alone?

Define by genus and difference: what kind of thing it is, and what sets it apart.

- Weak: *Invoices are generated by the billing system and represent the amounts that customers are expected to pay.*
- Strong: *A bill for one billing period that cannot change after it is finalized.*

The weak one describes the system. The strong one defines the thing, and carries the rule that prevents the bug.

## Say what it is not

Most mistakes come from two concepts the model blurs together. A single Not sentence fixes that class of mistake permanently:

- *Not a [receipt](receipt.md): a receipt records a payment, an invoice requests one.*
- *Not a [team](team.md): a team groups people inside a workspace; the workspace is the tenant boundary.*

Write one whenever you catch yourself explaining the difference to a person.

## Choose connections by the test, not by completeness

A connection is a claim a reader needs to use the concept correctly. Everything else is a link in the body. "Invoice is related to Customer" is not a connection; "Part of a workspace, never of a user" is. If you cannot say why a reader needs it, leave it out.

A long list of connections usually means the concept is two concepts. Split it.

## Prefer a type, and write the claim

Start every connection with one of the eight openers, then say the claim, with conditions and differences after the colon:

- *Requires a [proration](proration.md) for any change after it is finalized.*
- *Part of a [draft invoice](draft-invoice.md) until finalization, then part of a [credit note](credit-note.md).*

A sentence that stops at the opener, like "Requires proration", has the type and not the meaning.

## When a relationship has substance, make it a concept

Settlement is the relationship between a payment and an invoice. Entitlement is the relationship between a customer, a plan and a feature. Each has rules of its own, so each gets a file, with simple connections to the things it relates. This is how three-way and four-way relationships work too: the relationship becomes a concept with one connection per participant.

## One word, one meaning

The titles of a base are its vocabulary. Use a concept's title every time you refer to it, in concepts, in code review, in prompts. Declare other names once, with "Also called", and never use them in prose. If two things share a name, give one of them a new name; two concepts called Account are a sign that one of them is really Ledger Account.

## Keep sources, never copies

A concept points to the code, document or URL that defines the thing. It never reproduces it. Copies drift from the truth; a source line stays true, and when the source changes the concept is the first thing to re-read.

## Start small and grow from corrections

Ten to twenty concepts: the terms used everywhere, the terms with two meanings, the terms nobody has written down. Then stop. The base fills in on its own, because every time the agent misunderstands something, the fix is a concept. A base written all at once is a glossary nobody maintains; a base grown from corrections contains exactly what caused trouble.

## Folders are for finding, connections are for meaning

A folder answers "where would I look for this". It does not say what a concept is. A concept lives in one folder and connects to concepts anywhere. When a folder passes about thirty concepts, give it its own `index.md`, and keep the root map as a list of folders.

## Keep the map small

The map is the only part of the base that costs tokens on every turn. One line per concept, the definition, the connections, nothing else. If the map passes about 4,000 tokens, split into folder maps. Never put a diagram, an essay or a changelog in it.

## Do not put these in a concept

- **Instructions.** "Always run the tests" belongs in `AGENTS.md`.
- **Procedures.** "How to issue a refund" is a skill.
- **Preferences.** "I like short variable names" is for your own instructions file.
- **Status.** "Currently broken" is an issue, not a meaning.
- **Copies of documentation.** Link to it from a source line.

A concept says what a thing is. When a file starts saying what to do, it has stopped being a concept.

## Review concepts like code

A concept change goes in the same pull request as the code that changed its meaning, and reviewers read it the same way. A reviewer who disagrees with a definition has found either a bug in the concept or a disagreement in the team, and both are worth finding before the code ships.
